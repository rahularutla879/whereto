## Original bypass and current privileges

V1 granted the runtime worker SELECT on all operational tables, INSERT on sessions/capabilities/operations/facts, UPDATE on sessions/gate, CRUD on evidence, and sequence USAGE. Triggers protected existing anchors from UPDATE/DELETE, but an arbitrary worker INSERT could invent a reservation, consume a capability without its checks, append an unauthorized outcome, or bypass the Python financial totals and fence checks. The trusted worker was part of the accounting boundary.

The disposable fixture now separates three principals:

| Principal | Minimum authority / responsibility |
|---|---|
| Synthetic bootstrap administrator | Creates fixture database roles, initializes immutable policy, owns database and injects deliberate fault states in tests. Never used by `LocalPostgres`. This superuser exists only inside the disposable container. |
| `whereto_synthetic_owner` | NOLOGIN; owns schema, tables, sequences and routines. No SUPERUSER, CREATEDB, CREATEROLE, REPLICATION or BYPASSRLS. Bootstrap grants database CREATE to install its isolated schema. Runtime has no membership or SET ROLE permission. |
| `whereto_synthetic_worker` | LOGIN and database CONNECT, schema USAGE, EXECUTE on exactly `synthetic_state.protocol(text,jsonb)`. No table/sequence privileges, schema/database CREATE or TEMP, role management, owner membership or function grant option. |

PUBLIC database privileges and public-schema CREATE are revoked in this **new fictional database**. All operational function EXECUTE defaults are revoked from PUBLIC, including helpers; future owner-created functions in this schema also default to no PUBLIC EXECUTE. Bootstrap installs schema/routines/policy/grants in one transaction. No permissions are changed in the owner's Supabase database.

The seven protected tables remain `policy`, `gate`, `sessions`, `evidence`, `capabilities`, `operations`, `facts`. There are no worker-visible table views. The worker obtains only scope-bound evidence through `read` and sanitized totals through `snapshot`. It cannot directly SELECT protected tables, INSERT, UPDATE, DELETE, TRUNCATE, change triggers, advance/reset the sequence, alter the routine or become its owner.

## Database-enforced transitions

`routines.sql` implements one fixed, bounded SECURITY DEFINER entry point, with allowlisted commands and exact per-command JSON keys. Commands are `check`, `create`, `claim`, `read`, `revise`, `revoke`, `issue`, `reserve`, `transition`, `snapshot`. Unknown commands, null/missing/extra arguments and invalid scalar bounds refuse. Internal `valid_integer` and `abandon` helpers cannot be executed by the worker. There is no dynamic SQL, arbitrary table/query argument, force/resume action or policy-update endpoint.

The function fixes `search_path=pg_catalog,pg_temp` and qualifies every application relation/helper by schema. Its non-login owner, not the caller, supplies table privileges. The caller cannot replace the routine, create shadow objects in the protected/public/temp schemas, gain owner membership or change its security settings. This follows the [PostgreSQL SECURITY DEFINER guidance](https://www.postgresql.org/docs/17/sql-createfunction.html) and [ownership/privilege model](https://www.postgresql.org/docs/17/ddl-priv.html).

Every command locks the same `gate` row and requires READ COMMITTED before examining protected state. The routine verifies the installed version, policy shape/bounds, gate presence and reservation/fact consistency; Python `check` additionally requires the expected fingerprint and limits. Reservations atomically enforce aggregate and provider gross/attempt caps, active-operation concurrency, current session/revision/fence, capability purpose/binding and operation/capability uniqueness. SQL never accepts client-supplied totals. Inserts of charge and RESERVED fact commit together. Unique constraints remain a second replay barrier.

`claim`, `revise` and `revoke` fence previous workers and append UNCERTAIN for abandoned RESERVED/INTENT operations. Revisions do not extend absolute expiry or reset spending. Only the current session/revision/worker/fence may append INTENT and a legal terminal outcome to its bound operation. A failed or uncertain operation retains the full charge; uncertainty never becomes retryable or free capacity. Revocation is allowed even when evidence is unavailable so it can disable authority safely.

Evidence now has a protected database SHA256 over PostgreSQL's JSONB text representation. The function computes it on create/revise and checks it before claim/read/issue/reserve/transition and **before revision replacement**. The worker cannot update either payload or digest directly. Missing or altered evidence refuses even when calling SQL without Python. The existing Python canonical DTO/HMAC check remains on read, including private/excluded fields. Ordinary/advanced/pending/options/selection kinds and capability purposes remain distinct. Non-ordinary kinds cannot reserve synthetic provider work.

`postgres.py` now only serializes existing DTOs, hashes bearer handles, retains instance/process lease checks and invokes the routine in explicit transactions. It contains no operational INSERT/UPDATE/DELETE or financial decision implementation. SQL is the authoritative state machine, rather than a parallel Python writer. Error handling returns fixed refusal/unavailable codes without SQL exception text. Database failure has no memory fallback. No changes to actual application source, dependencies, schema, frontend or startup guards.

## Security limits and operational requirements

- The database protects the **local protocol**, not the truth of an AI extraction. Runtime can submit new fictional evidence through create/revise. The routine checks kind, bounded object payload, scope, digest and transition invariants; it does not implement Pydantic's complete semantic validator in SQL. Future real issuers must prove validation/source ownership separately. All `Reservation.planning_authorized` values remain false; providers are synthetic IDs only.
- Gross charges remain caller-supplied fictional integer reservations under immutable synthetic caps, as in V1. Zero-charge attempts still consume attempt/concurrency allowances. No real provider price, unit/window/day/outing policy or financial grant is supplied here. A future live reservation must derive charges from protected unit/rate policy, not trust a runtime quote. This remains a deployment blocker.
- Owner/bootstrap privileges can change routines or table contents and are outside the hostile-runtime threat boundary. The owner role must stay NOLOGIN, ungranted to runtime; bootstrap credentials must remain separate. In this test harness the test process deliberately has synthetic admin credentials for setup/fault injection; it is not a production secret-isolation model. No real keys or accounts are enrolled.
- A runtime principal that legitimately owns a bearer session can create a new revision, claim a newer fence, or report its own outcome. SQL cannot independently attest that an external send occurred or succeeded. It cannot prevent malicious code from performing network I/O outside this absent transport. Actual provider egress/admission must later be joined to committed authority; no exactly-once HTTP claim.
- A credential holder can still cause denial of service by holding a transaction open or repeatedly claiming a session it owns; workload identity, bounded connection/session lifetime and abuse controls remain hosted requirements. No availability guarantee against a malicious runtime principal is claimed.
- SQL evidence digests detect payload corruption while protected digest metadata remains intact; they do not resist a malicious administrator rewriting both. Existing HMAC binding remains distinct. This is not encryption or a real private evidence-retention solution.
- No hosted pool/TLS/role mapping, Redis adapter, cleanup policy, stable key lifecycle, restored-backup replay reconciliation, uncertainty operator or multi-instance session integration is implemented. Global locking/history scans remain a correctness reference, not a throughput guarantee. Local crash tests do not prove power-loss durability or hosted failover.
