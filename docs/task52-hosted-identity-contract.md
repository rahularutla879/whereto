## Two independent identity boundaries

### Google workload OIDC

`tokens.py` uses hash-pinned **PyJWT2.15.1** with existing experimental cryptography wheels; no application/deployment dependency lock is changed. Production `Tokens(GoogleKeys())` verifies only fixed Google HTTPS key origins, exact configured audience/issuer, RS256 workload signature and integer issue/expiry/subject bounds. The separate dormant `HostedAuth` boundary additionally checks the enrolled immutable service-account subject **and** exact verified email, caller allowlists and request/user proofs; it rejects fixture enrollment. Workload roles derive from server enrollment and method allowlists, never caller-supplied email/role headers. Revoked principals refuse. Public key discovery never uses a token's URL, `jku`, `x5u` or unverified issuer. Unknown keys do not create an alternate trust source.

The fixed-origin cache verifies HTTPS, rejects redirects/non200/oversized documents, bounds key count and algorithms/types/private parameters, honors bounded Cache-Control lifetime and refuses expired keys without fallback. Unknown-key refresh is rate-bounded to once/minute; this can temporarily refuse legitimate rotation and must be measured operationally. No real key endpoint was contacted. Transport mocks exercise parser/cache cases, not Google connectivity or real key authenticity.

`OfflineKeys` is an explicitly distinct fixture type, requires an isolated Docker loopback environment, rejects production/hosted indicators, and carries a mandatory fixture marker. Fixture kids start `task52-offline-`. The default production verifier rejects fixture sources and kids before network access. Local RSA/EC fixture private signers remain in the disposable test controller, not frontend/backend/authority configurations or Git. Existing parent synthetic JWTs are not accepted as Google identity. The entire offline server/bootstrap is unavailable in known hosting/production environments.

Google ID tokens are reusable bearer identities, not exact request approvals. A separate per-workload Ed25519 request proof binds exact service audience, method/path/body digest, Google token hash, user-forwarding hashes, build/environment/epoch, expiry≤60s and one-use nonce. These are application proof keys, **not service-account JSON keys**. Each receiving service verifies its enrolled proof key and Google identity independently, then consumes a protected nonce in independent witness PostgreSQL. Workload identity never replaces source/evidence/admission/financial/canonical-payload checks.

### Direct Cloud Run IAP user assertions

The selected configuration is **direct Cloud Run IAP**. Its signed assertion is ES256 with issuer `https://cloud.google.com/iap`, the separate IAP JWKS, and audience `/projects/PROJECT_NUMBER/locations/REGION/services/FRONTEND_SERVICE_NAME`. It is not an OAuth client ID, load-balancer backend ID or downstream service audience. The implementation bounds assertion lifetime to 660s, requires current expiry and tightly bounded issue time, and enrolls exact tester subjects. Email/domain headers do not establish identity. IAP itself can inject unsigned user/email headers: the frontend ignores and drops those headers rather than rejecting legitimate IAP traffic or trusting them. The backend/factory require the signed assertion and reject unexpected unsigned identity forwarding. Opaque session ownership derives from verified issuer/audience/subject, not mutable email or workload identity.

The frontend independently verifies the raw IAP assertion, then signs a short-lived **user-forwarding scope** with its own proof key. It binds the IAP assertion hash, exact application path/body, build/environment/epoch and nonce. Backend and factory each independently verify the IAP signature/issuer/audience/subject and frontend signature/scope. Each consumes the forwarding nonce in its own service namespace. A backend cannot substitute another valid user's assertion, alter the body, reuse the scope on another session, or mint frontend scope with its own key. Counter/dispatcher receive only their necessary authenticated action payloads, not an assumed end-user identity.

IAP assertions themselves are bearer credentials and are not request-bound. In hosting, direct IAP must cover every frontend ingress and only the IAP service agent may invoke the frontend. The local fixture explicitly simulates this platform gate with a separately signed offline IAP-agent ingress identity held only by the controller. It is never forwarded downstream or treated as a production/browser-trusted header. A backend that merely captured a user's IAP assertion cannot enter the fixture frontend without that separate identity. This tests the boundary but does not verify real Cloud Run IAM/IAP behavior.

Private staging testers need owner-approved IAP access; this is not a permanent Where To? registration system. Existing anonymous saved links remain capability-authorized data: an authenticated tester without the saved bearer still cannot read/refresh it. Conversely, possession of a bearer never establishes a planning account or original interpretation. Public anonymous access versus IAP exposure at launch remains a separate owner decision; no current local behavior changes.

## Exact request flow and custody

Browser → IAP-protected frontend → Google-authenticated backend replica → trusted native factory/issuer → separately authenticated counter/dispatcher → synthetic provider. Independent recovery remains a separate workload/operator boundary.

| Workload | Credentials / authority in this fixture | Never receives |
|---|---|---|
| Frontend | Own workload token/request-proof key; IAP/public workload keys; no SQL/Redis credential | Operational SQL, issuer, provider, Redis or recovery administration; IAP/Google fixture signers |
| Backend A/B | Same logical backend service identity with own request-proof keys; own nonce/epoch witness login | Frontend signing key, operational/issuer/counter/delivery/financial/recovery credentials; fixture signers |
| Factory/issuer | Existing restricted native/action/financial SQL and encrypted evidence; own proof key and limited witness phases | Counter login, provider credentials, recovery/owner administration |
| Counter | Existing protected count login + own nonce/epoch | Issuer, Redis, delivery, grants/rates/recovery authority |
| Dispatcher | Existing delivery-only SQL/witness + evidence read + own proof key | Reserving/counting/grant/epoch authority; no real provider credential here |
| Recovery | Existing stop/epoch/quarantine operator routine, operator-only caller allowlist | Financial grant creation/refunds/reactivation or application planning |

Backend replicas share the logical service-account identity, not an end-user identity. The frontend has no database or Redis credential. It binds its reviewed epoch configuration in the forwarding proof; backend and factory independently validate current witness epoch before any native/financial action. The backend authentication-only SQL login can read epoch and consume its own service nonce namespace; it cannot mutate/query operational history or administer witness/grants. Giving the backend a nonce-only login is an explicit increase from the frozen parent's credential-free worker fixture. It adds durable authentication replay/epoch access, without issuer, count, delivery, financial administration or private operational-evidence privileges. New `nonce.sql` is installed only on fresh disposable witness databases. Roles use SCRAM, fixed SECURITY DEFINER search paths, immutable history and bounded nonce storage. No in-memory replay fallback or automatic pruning exists. A compromised workload with its nonce-only login can burn its namespace or exhaust the shared 10,000-record fixture bound, causing refusal; it cannot turn that denial into financial authority. Hosted rate limits, connection budgets and reviewed nonce maintenance remain required. Nonces survive operational SQL rollback because they live outside it; witness/epoch administrative compromise remains outside the local guarantee.

Native opaque tickets, absolute expiry, current revision/fence, encrypted Redis commitments, original root/outing and restore epoch remain checked by unchanged parent factories. One user's ticket cannot be used by another; replicas may continue the same user. Reusable selected receipts remain reusable; purpose-specific refresh still performs fresh access/RLS/expiry/membership and durable consumption. No input may choose prices, root, grant, untrusted graph or provider payload. Authentication success is not spending or planning permission. The known legacy ordering loss, frozen V5.1 evaluation and original historical classifications remain unchanged.
