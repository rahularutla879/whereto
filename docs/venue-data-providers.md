Foursquare's legacy V3 retirement and June pricing changes make old API examples unsafe starting points. Its API licensing requires branded attribution and account-specific caching/query limits. [Current transition/pricing notice](https://docs.foursquare.com/developer/reference/upcoming-changes), [API overview](https://docs.foursquare.com/fsq-developers-places/reference/places-api-overview), [API license](https://foursquare.com/legal/terms/apilicenseagreement/).

OSM allows data reuse under ODbL, with attribution and share-alike obligations where applicable. It is a dataset, not an unlimited hosted Places service. Nominatim's public server prohibits systematic POI downloading and is not the recommended source for this planner; its one-request/second ceiling is not an Overpass allowance. A hosted/self-operated query service would need an independent capacity agreement. [OSM copyright](https://www.openstreetmap.org/copyright), [license FAQ](https://osmfoundation.org/wiki/Licence/Licence_and_Legal_FAQ), [public Nominatim policy](https://operations.osmfoundation.org/policies/nominatim/).

Geoapify offers convenient radius/category queries. Its credit accounting varies with result count, not simply one credit per HTTP call. Free-plan attribution and commercial-use qualifications remain applicable. [Places API](https://apidocs.geoapify.com/docs/places/), [pricing](https://www.geoapify.com/pricing/), [terms](https://www.geoapify.com/terms-and-conditions/).

TomTom now recommends Places Search for new integrations; the older POI Search documentation still describes usable category/geographic controls. Static documentation does not prove the selected plan's paid price, retention rights or actual account quota; obtain those before activation. [POI Search](https://docs.tomtom.com/search-api/documentation/search-service/points-of-interest-search), [current pricing](https://docs.tomtom.com/pricing).

## Recommended future proof of concept

**Geoapify, as a separately approved, small coverage comparison**, rather than automatic runtime fallback. Its bounded circle/category queries align with the nearby-coverage question and the published free credit model is easy to account for. It may share OSM's gaps; no claim it beats Google in Kothapet. Compare independently obtained venue IDs/evidence around a public reference in Hyderabad and Manhattan, manually assess relevance, duplicates, missing/closed establishments and coordinates, and measure requests/credits/latency. Do not enable paid plans or use the full public free rate automatically. Owner approval for accounts/credentials and provider-specific terms must precede any live experiment. Foursquare is a second candidate if dining/nightlife gaps remain after measurement; commercial enrichment costs need separate approval.

## Future provider-neutral architecture (design only)

Extend the existing normalized facts without writing a second planner:

1. `DiscoveryIntent(activity, originalPhrase, geometry, hardGeography, cursor, actionBudget)` requests explicit capabilities: text/category, circle/rectangle/area, page limits, languages. An adapter must refuse unsupported restrictions rather than simulate verified boundaries.
2. `VenueObservation` contains a namespaced stable identity (`google:...`, `fsq:...`, `osm:node/...`, `tomtom:...`), provider IDs, optional coordinates/address, category evidence, provenance per field, confidence, missing-field states, attribution and a source-specific retention policy. No alternative-source venue is assigned a fictional Google Place ID.
3. `DiscoveryPage` contains observations, opaque provider cursor, observed counts, stop reason and measured usage. Pagination, concurrency, timeouts and cancellation remain action-bounded; separate SKU/credit rates feed the existing durable accounting design.
4. Entity resolution uses each source's IDs first; cross-source matching considers normalized names, address/branch evidence and proximity, with explicit confidence. Nearby chains and separate departments cannot be merged solely on distance. Conflicting observations remain separate evidence, not overwritten “truth.”
5. Provider-specific attribution travels with every displayed fact. Separate retention/cache adapters enforce each license; never build a durable merged Google database by borrowing OSM's permissions.
6. Routing accepts coordinates when no Google ID exists. Google technically accepts coordinate waypoints; this does **not** grant permission to combine every vendor's content. Review both agreements and keep source labels separate. Google Routes output requires its own attribution and must use a Google map if displayed on a map. [Routes location inputs](https://developers.google.com/maps/documentation/routes/specify_location), [Routes policies](https://developers.google.com/maps/documentation/routes/policies).

No source verifies tickets, reservations, class sessions or exact spending merely by locating a business. Independent provider routing/data-use review, owner authorization and fixture tests are prerequisites to a future adapter. No Task 47 work is included.

## Google Nearby Search assessment (not enabled)

Nearby Search New supports type-filtered circles and distance ranking, so it is a reasonable future comparison for local restaurants/bars around Kothapet. It returns at most 20 per request and does not expose Text Search's page-token workflow; broader coverage would require separately bounded region queries. It is a different billable method, with its own field/SKU and quota review, and is **not authorized or called here**. It would not verify ten-minute road travel or arbitrary custom class availability. Existing Text Search now uses coordinate-centered restrictions without conflicting city-wide wording when the anchor is compatible. Google documents that explicit location text can override a bias; the current integration uses restrictions and does not equate bias with a hard boundary. [Nearby Search New](https://developers.google.com/maps/documentation/places/web-service/nearby-search), [Text Search New](https://developers.google.com/maps/documentation/places/web-service/text-search).
