## Refresh decision and scope

The owner explicitly approved purpose-specific refresh without the original interpretation, which saved documents intentionally omit. This is documentary product/security direction, not a signature, independent review or financial grant. `Broker.refresh` independently reopens the document; rejects an unselected candidate/non-real document; binds the full current document hash and explicit request; and restricts all Details to selected allowed venue IDs. It reopens and compares the current document **before every reservation and dispatch**, so revoked access or changed selection blocks further work. RLS/expiry are delegated to the unchanged actual saved-plan access implementation; tests inject only synthetic returns/errors, not a real database.

A protected stable-key HMAC binds access capability plus refresh ID. SQL claims this identity atomically with the first successful reservation for 1800 seconds, matching native replay retention. Another Broker with the same server key cannot reset it. Native fresh-outing-per-explicit-refresh behavior and shared session budget are retained. Admission failure before reservation creates no claim; once charged, uncertain attempts retain it. Reusing an expired refresh window does not confer access: all current document/capability checks run again. No discovery, fresh interpretation, added venue or unrestricted planning is authorized.

Current saved DTOs have no revision counter: an exact document digest is the revision identity here. Do not claim a nonexistent saved database revision field. Separate real cross-instance refresh/session ownership and transactional reread/dispatch integration require review before hosting.

Builders immediately return `None` when inactive, preserving normal serialization/error precedence. Existing actual request builders attach payloads at `OutingBudget.reserve`/`reserve_matrices`. Existing transports consult the seam before their existing credential/network paths. Normal startup does not import or construct the experimental Broker.

`experiments/shared_state/action_bridge.py` composes actual validators, ordinary/advanced planners, options, lookup, contact and refresh. Its constructor requires a container with loopback as its only interface, an exact reviewed build, supplied fake model/responder and separate synthetic issuer connection factory. It offers no browser-selected callback/extraction/plan grant. A nonblocking action lock and ContextVar ownership prevent concurrent/nested reuse of its mutable dispatch batch. Source snapshots are deep-copied, integrity-sealed, expire after 600 seconds, and are invalidated by source replacement/revocation. A pending answer increments the source revision; unchanged matching pending never calls the model again. Separately supplied existing execution controls are retained as sealed owned evidence, validated with the same allowed keys and actual PlannerInput when complete. Each interpretation revision is consumed for planning before attempting work, including pending completion, so exceptions cannot turn into free replay. A validated pending advanced handoff may create its native Session under the separate pending purpose; it never fabricates the original raw receipt.

`LocalIssuer` alone receives the fixture issuer connection factory; runtime role objects receive no issuer connection. It binds native OutingBudget object identity to a stable SQL outing within a logical protected budget root. Request plans derive from existing server-built payloads and native operation/dimensions, not caller prices. SQL still computes all charges from protected V3 rates and scope policies. Nothing activates the standalone dollar guard or borrows the AI evaluation allowance.

`bridge.sql` adds immutable action registration and refresh claims to the existing protocol. Only the separate NOLOGIN issuer can register an action or approve plans. Runtime can execute only the new `bridge_protocol`; old core/financial entry points and direct table mutation are revoked. Reservation and dispatch check action identity, current evidence, revision/fence, active owned HTTP admission and current worker; completed inference leases, when applicable, must match the original source fingerprint. The existing common gate, protected unit pricing, caps, intent/outcome state machine and uniqueness rules are reused.

## Canonical requests and failure rules

Canonical UTF-8 JSON uses sorted keys, compact separators, finite numbers, an exact operation/method/URL/field-mask/body envelope and a 64 KiB bound. SHA256 binds the complete immutable bytes. The envelope retains query, pagination, included types, search geography/radius, field masks, Matrix origin/destination cells, travel/routing mode and departure parameters. Details binds the exact ID, GET method and mask. Required matrix fields and geometry are checked by the existing validator; dimensions and Drive/Walk SKU are checked before issuer approval. Existing source-specific Search/lookup/Details masks are allowlisted. No canonicalization rewrites or repairs a request.

All planned matrix HTTP requests reserve atomically as before. Before calling the fake responder, both byte equality against the owned batch and SQL equality against the reserved line digest are required. SQL enforces sequential once-only dispatch ordinals. Missing reservations, changed body/method/mask/location/dimensions, revoked source/admission, missing evidence, wrong revision/fence or replay refuse. Digest equality alone is never interpreted as source authority.

Reservation → committed INTENT → committed dispatch fact → fake responder → terminal outcome. An exception/unknown response is UNCERTAIN with retained charge and no automatic retry/refund. An interrupted batch retains the entire conservative reservation. Cleanup revokes the short-lived action and releases HTTP ownership even when work fails. A dead worker cannot turn its reservation back into free work. SQL failures never fall back to local authorization. Abandoned active HTTP leases can retain capacity after a crash; reviewed reconciliation is still needed for hosted availability, rather than automatically freeing uncertain authority. Existing cancellation scopes still run around the actual native operations; this checkpoint does not claim distributed cancellation or exactly-once external execution.
