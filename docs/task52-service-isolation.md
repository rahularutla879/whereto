# Task 52 — authenticated local service isolation

Baseline: `82047f58518788e4cf139d94ac00555049f59c30`. Profile: **52-service-isolation-local-v1**. This is an inactive, synthetic-only checkpoint. No normal application import, public endpoint, deployed service, production credential, hosted model, financial grant or real provider transport is added. Exact source/build digest and completed verification are recorded in [verification](task52-service-isolation-verification.json) and [manifest](../experiments/service_isolation/build.json).

## Acceptance and existing boundary audit

The native parent already checked encrypted evidence, revision/fence, absolute expiry, source integrity, immutable checkpoint commitments, outing/root identity, protected SQL accounting and an independent witness. Its test composition nevertheless handed the same Python process a NativeIssuer, counter connection and witness operator supplied by the harness. A malicious ordinary worker in that process was outside its guarantee. A Python private attribute is not a credential boundary.

This profile keeps the tested financial algorithms and native factories unchanged. It moves their composition into separate restricted containers/processes with authenticated interfaces. Success requires owner-bound native continuation on another worker, refusal of unauthorized calls and SQL bypasses, durable replay protection, and retained charges after interruption. Local isolation is not hosted readiness.

## Service, role and credential matrix

| Process | Permitted responsibility and credentials | Explicitly absent |
|---|---|---|
| Ordinary workers A/B/other | Own synthetic Ed25519 workload key, public enrollment/CA; fixed enrolled synthetic owner | SQL, Redis, evidence encryption/HMAC, issuer, counter, dispatcher, recovery/operator and provider keys; other workload private keys |
| Factory/validated-action issuer | Existing native factories, application validators, planners and admission; restricted SQL runtime and issuer logins; encrypted Redis keys; limited checkpoint/reserve/dispatch/outcome witness login; own workload/TLS key | SQL owner/admin, token-counter login, delivery login, recovery/operator login, real provider keys |
| Trusted counter | Exact canonical fictional inference counting; counter-only SQL login, independent epoch/own-service nonce login, own workload/TLS key | Source issuance, reservations, delivery, Redis encryption, policy/grant administration and recovery |
| Canonical dispatcher | Exact approved payload delivery; delivery-only SQL login; encrypted evidence read keys; deliver-only witness login; own workload/TLS key | Approving actions, reserving money, counting tokens, changing grants/rates/epochs, SQL admin and real provider keys |
| Independent recovery | Witness operator and replay-nonce login; own workload/TLS key; only separately enrolled operator may call | Application/issuer/counter/delivery credentials; operation, pricing, refund or grant-renewal API |
| Disposable bootstrap/operator | Creates fictional schema, roles, grant, workload keys and local CA; synthetic operator key held only by private test controller | Never supplied to a worker or copied into the shared read-only code volume |

Factory and action issuer are one deliberately trusted domain: existing validation runs inside the authority that approves the resulting request plan. Moving only an approval function while trusting a worker's claimed validation would not establish authority. Counter, delivery and recovery remain independently credentialed. Compromise of trusted validation code is a residual risk; this does not prove a malicious issuer tells the truth.

Each role runs as UID10001 with its own PID/filesystem namespace, read-only root/code volume, dropped capabilities, no privilege escalation, private tmpfs, no Docker socket, no host mounts and no published ports. Services share only the disposable PostgreSQL loopback network namespace, containing no external interface. Bootstrap is privileged test administration outside the threat model. Host/Docker administrators can defeat this local isolation.

The older trusted fixture allowed PostgreSQL loopback `trust` authentication. Credential separation would be ineffective with that setting. This new profile supplies `POSTGRES_INITDB_ARGS=--auth-host=scram-sha-256` to **both newly created** databases, verifies all TCP rules require SCRAM, and tests wrong-password administrator/issuer/counter connections from an actual worker plus anonymous Redis refusal. Unix-socket bootstrap administration remains inside the private database container filesystem, which workers cannot mount. Redis has separate epoch/namespace-scoped factory publication and dispatcher read-only ACL users. Neither receives the bootstrap administrator password; CONFIG, ACL and FLUSH commands refuse, as do dispatcher writes and out-of-scope keys. The private ACL file is installed before Redis starts and retained on its own restart; it is never mounted into workers or committed. Frozen parent harnesses are not rewritten or claimed to isolate hostile loopback workers.

## Authentication contract

`auth.py` uses separate short-lived synthetic Ed25519 workload identities over certificate-verified TLS. A private one-day fixture CA issues service-specific DNS SAN certificates. Each caller knows the public CA and its own private workload key. No CA private key is distributed. TLS verifies the selected service identity; there is no insecure TLS, redirect or alternate transport fallback.

A signed envelope has an exact JWT header (`EdDSA`, `JWT`, enrolled principal key ID) and exact claims: issuer, principal, role, audience, issue/expiry times, nonce, build, environment, restore epoch and request digest. Verification requires the enrolled key/principal/role, exact target service and per-path caller allowlist, current independent epoch, exact profile/environment, integer times (at most60 seconds lifetime, five-second future tolerance), and a32-hex nonce. The digest binds audience, POST, path and SHA256 of exact canonical body bytes. Strict JSON rejects duplicate keys, noncanonical data and malformed/extra fields. Request bodies are capped at200KB, responses at1MiB and tokens at8KB. The existing synthetic ordinary plan DTO measures269,683 bytes: a shared200KB request/response cap refused a valid plan. The new response bound preserves the existing DTO without changing request or encrypted-record limits.

A successful authentication consumes a protected SQL nonce before any action, including an action later refused. Replay with a new connection/worker/service restart is rejected. All authentication nonces live in the independent witness database, so operational database rollback cannot erase them. Each SQL login may consume only the nonce namespace of its own service. Tables are append-only; each store is bounded at10,000 nonce records and refuses when full. Automatic pruning is intentionally absent. Reviewed maintenance/retention is a hosted prerequisite. Authentication is necessary, never sufficient action or spending authority.

Only fixed POST methods exist. No SQL, signing, pricing, generic HTTP, arbitrary response callback or provider-operation endpoint is exposed. Missing/incorrect authentication returns a generic refusal; errors log static reason/stage/SQLSTATE and source frame names, never bodies, tokens, evidence, credential values or database messages. Network/SQL failure refuses without in-memory authorization fallback.

### Mapping to Cloud Run — not implemented

The local issuer is a fictional trust root; its tokens are not Google identity tokens and must never be accepted by a hosted verifier. Hosted services require distinct service accounts, exact-audience Google-signed ID tokens, restricted `roles/run.invoker`, verified issuer/signature/expiry/principal, private routing and appropriate ingress. The signed action/body/nonce and SQL/evidence checks remain application requirements beyond IAM. No service-account JSON key, metadata token call, Google SDK or account change is introduced here. See official [service authentication](https://docs.cloud.google.com/run/docs/authenticating/service-to-service), [service identity](https://docs.cloud.google.com/run/docs/securing/service-identity) and [audiences](https://docs.cloud.google.com/run/docs/configuring/custom-audiences).

The fixture maps workers A/B to one fixed fictional owner and a third worker to another. This proves cross-worker ownership checks, not authentication of a real end user. A real worker workload identity alone cannot vouch for arbitrary browser identity: independently verified IAP/end-user ownership and a reviewed forwarding contract remain mandatory.

## Native ticket routing and action flow

1. An enrolled worker submits a typed request and permitted existing deterministic controls, not a raw extraction/graph/checkpoint/root. A canonical UUID initial-request ID is consumed durably per enrolled owner **before** inference. A fresh credential cannot repeat that same request after a lost response. This is idempotency, not authorization; different IDs do not reset SQL grant/root/outing limits.
2. The factory runs the actual InterpretationInput/PlannerInput validators and original Broker/native code. Only the separate counter can register exact fictional input bytes. Existing SQL policies bind model/prompt/schema/rates and conservative output cap before reservation. Fictional UTF-8 byte accounting is **not** provider tokenization.
3. Native Source/advanced/history/Details dependencies use existing approved factories, not object deserialization. The outer owner-bound opaque ticket indexes an AES-GCM encrypted locator. SQL commits owner, native checkpoint, build/epoch, revision, expiry and ciphertext hash. Browser/native internal tokens stay server-owned. The outer service profile binds the unchanged parent native graph identity, rather than relabeling the frozen parent build.
4. Lookup checks current SQL/Redis/witness and fences prior worker authority without new provider work. Mutating continuation first consumes an immutable `(route, revision)` turn. Missing evidence or an interrupted turn blocks; no automatic reconstruction through provider calls. Clarification reuses original interpretation without another model request. Advanced handoff, answer/plan/advance/more/contact use existing native methods.
5. The trusted issuer approves source-owned exact provider payloads at the existing planner/budget seam. SQL preserves current admission, protected unit plans, root/outing/grant, capability, revision/fence, reservation, intent and canonical payload identities.
6. Before remote delivery the factory creates an opaque, one-use in-memory proof of its currently active validated action. The dispatcher authenticates the factory, decrypts source evidence, and calls back on a dispatcher-only authenticated method to consume that exact operation/ordinal/digest proof and rerun current source/access validation. The callback cannot create approval. Factory restart loses pending proofs and refuses. Separate bounded callback capacity avoids circular service-slot deadlock.
7. The dispatcher uses the existing GrantService delivery algorithm with a narrowly versioned SQL connection adapter. It rechecks current encrypted evidence, fence/epoch, exact reservation/payload and once-only durable delivery. New delivery-only SQL also rechecks active HTTP and, for inference, inference admission immediately before delivery. There is no live transport or credential loader; only the fixed synthetic responder can run.
8. Reusable selected receipts have separate selection-only routes; selection does not become single-use spending. Purpose-specific refresh reopens current synthetic saved access on every action and preserves selected venue membership/expiry/durable refresh consumption. It never claims omitted original interpretation evidence.

A process dying after current action approval cannot recall an already accepted in-flight operation; one authorized operation may finish. Lost responses do not trigger retries. Unknown initial results require reviewed recovery or a new legitimate user action within the unchanged limits, not silent resend. All diagnostic planning/legacy limitations remain as in the native parent, including optional-coffee legacy order loss; no ordering policy is repaired or activated here.

## SQL and recovery boundary

`protocol.sql` adds protected profile, initial-request, route and turn facts. `witness.sql` holds the independently retained authentication nonces. Runtime workers have **no database connection**. The issuer gets only its existing restricted EXECUTE privileges plus the two specific service routines. Delivery gets only its restricted service wrapper/accept-delivery routines; direct table DML, reserve, count and approve remain denied. SECURITY DEFINER routines use fixed search paths and qualified objects, immutable records, existing locks/transaction checks and restricted ownership. No real schema migration is supplied or executed.

`witness.sql` permits the factory only existing checkpoint/financial-prefix phases, the dispatcher only delivery phases, and the counter only epoch reads and its own authentication nonces. Recovery requires its separately enrolled operator. Its API can rotate the epoch or append stopped/quarantined/reconciled-stopped events; it cannot refund, reactivate or renew. Epoch rotation quarantines the full synthetic grant. Redis loss cannot erase SQL exposure. An older operational snapshot disagrees with independent witness history and stops; coordinated witness rollback is covered by the unchanged parent recovery drills and external epoch conditions.

No ordinary process can reset grants by changing worker/session/root or appending nonce records. Charges stay conservative after missing response, failed delivery or uncertainty. A restored SQL nonce prefix does not authorize provider replay: independent financial/checkpoint prefix, consumed capabilities and epoch checks are still required. Privileged correlated database/epoch/backup compromise is outside this model. Hosted independently operated recovery, backup ownership, reviewed reconciliation and quarantine procedures remain outstanding.

A hosted pooler must preserve the restricted SQL login and `session_user` semantics; an administrator connection plus a caller header cannot replace them. - Application startup, deployment image allowlists, local Qwen/model/prompt, ordering, saved schema/RLS, financial policy and frozen source manifests are unchanged. Historical evaluation is a separate accounting domain.
