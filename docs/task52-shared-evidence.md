## Implementation

`experiments/shared_state/evidence_models.py` admits an explicit map of existing Pydantic classes plus bounded membership and reference-clock records. Canonical sorted UTF-8 JSON rejects duplicate keys, NaN, unknown model kinds and noncanonical representations; decode/re-encode must match. Private/excluded DTO fields are included in the encryption domain. There is no pickle, dynamic class path or executable deserialization. Raw extraction, effective pending and purpose-specific refresh have distinct provenance; pending cannot masquerade as fresh raw. Typed data is not itself semantic or planning authority.

`redis_evidence.py` uses the maintained `cryptography` AES-GCM implementation with a fresh96-bit random nonce, a32-byte key and authenticated associated metadata. AAD binds version, environment, external restore epoch, SQL session/revision/source binding, action digests, budget root/outing, key identity, generation and fixed deadline. Ciphertext SHA256 is committed separately in protected SQL. Keys are explicitly injected through a copied immutable key ring; neither SQL nor Redis stores encryption keys. No environment variable discovers a real key.

A record is at most64KiB plaintext plus28 bytes nonce/tag. One namespace admits at most350 records and128MiB ciphertext by default, with a four-connection bounded client pool. A Lua compare-and-set checks the previous exact ciphertext and uses Redis server TIME plus absolute PXAT expiry. Reads and rewrites do not extend TTL. Cleanup is bounded by350 expired index entries; index accounting is reserved before SET so a Redis memory failure is conservative. `noeviction`/memory errors refuse; they do not authorize re-fetching or remove SQL charges. Indexes retain only bounded expiry/size metadata, prune on writes and expire at the latest contained record deadline; encrypted record keys expire independently. Encryption/index/Redis overhead is additional to the payload quota.

Deadline calculations use the protected database clock, not a worker wall clock. Route deadlines are also bounded by each leg’s original aware `observed_at`; missing, stale or future observations refuse. Display result snapshots do not constitute a reusable live route cache. Source-owned deadlines remain SQL-bounded: ordinary/advanced/pending/options/selection600s; routes300s; Details/refresh membership can use1800s only under those exact purposes. The additive SQL front door permits that existing native reference lifetime; it does not extend ordinary sessions or financial leases. It leaves the frozen V4 routines unchanged. Key rotation explicitly rewrites under the new active key with a fresh nonce and CAS generation while retaining the original deadline. Read keys may overlap for a planned rotation; removing an old key immediately refuses old ciphertext. No silent fallback, TTL renewal or automatic re-encryption occurs. Removing a key stops new reads/attestations; already issued exact attestations have a maximum five-second life. Immediate operational revocation must also revoke the SQL session/pause issuance or replace its anchor, rather than assuming a local key-ring change remotely revokes an issued SQL fact.

The local adapter requires a container with only loopback networking and a fixed synthetic database/role. Redis connections are only loopback; a separate test-only TLS endpoint verifies CA/hostname and AUTH. It cannot connect to Memorystore by changing an environment flag. Isolated hash-pinned Redis/AEAD test dependencies do not change application/deployment/evaluation locks or images.

## SQL and Redis consistency / provider authority

`evidence.sql` is an additive local profile over the existing constrained financial/bridge routines:

1. SQL stores only the small typed `ProviderAction` digests, not original request text, coordinates or the Redis plaintext. The former synthetic UNLOGGED substitute is made LOGGED in this additive profile so digest metadata survives PostgreSQL crashes. Direct attempts to put private DTOs in SQL are rejected.
2. A separate NOLOGIN issuer commits the ciphertext digest, key ID, CAS generation, fixed expiry and epoch. Runtime cannot update anchors/policy, invoke the issuer functions, or call old core/financial/bridge front doors.
3. Before each reserve and each dispatch, a trusted `EvidenceVerifier` reads SQL metadata, fetches Redis, authenticates/decrypts the complete bundle, validates its types/provenance and rereads SQL. A short-lived attestation is created through the issuer-only routine for the **exact** command/parameters, current revision/fence and commitment.
4. The sole runtime SQL front door checks and atomically consumes that attestation with the existing financial transition. A remembered ciphertext digest is insufficient. Changed operation, capability, ordinal, payload digest, revision/fence, epoch, expiry, duplicate grant or replay refuses. The existing action/admission checks and protected request-plan/rate/unit accounting still run.
5. INTENT/outcomes and all committed charges remain append-only. Failed/unknown sends stay charged and cannot be resent automatically. No graph, DTO, checkpoint or compatible result grants planning authority.

SQL and Redis do not share a transaction. Publish Redis first, then CAS the issuer-owned SQL anchor. A crash between them leaves an uncommitted/mismatched blob and **blocks**; no automatic rollback or reconstruction is attempted. Failed publication before reservation creates no financial charge. Failure after reservation preserves it. SQL rereads/attestations close revision/fence races, but an outage can occur after a successful read; the exact five-second single-use attestation proves a checked snapshot, not continuous Redis availability. Once work is uncertain, record/retain uncertainty rather than retrying.

The synthetic issuer/verifier connection factory and keys inhabit the same test OS/process. This is not malicious-Python isolation or genuine workload enrollment. Production must place these authorities in the separately authenticated trusted service, protect keys and epoch ownership, and deny worker access to issuer credentials. SQL permissions are exercised with the real restricted local principal; the local callback is not a future public signing endpoint.

## Recovery and external epoch

Every connection requires a currently supplied epoch outside SQL and Redis. There is no implicit default, cached last-known epoch or in-memory fallback. Wrong, missing or restored epoch refuses. The harness restores an **older newly created synthetic schema** after consuming a capability and changing the external witness; the restored SQL cannot reuse the consumed authority. It does not copy or clone the real evaluation journal.

The external file in tests is a fictional witness, not a production tamper-proof epoch store. Hosted restore requires independent protected ownership, stop/revoke/drain before restore, a new epoch, and independent append-only exposure reconciliation or quarantine of the entire at-risk grant. An undetected database rollback with an unchanged external witness is **not automatically detected** by this prototype. No code may enable hosted dispatch until that operational boundary is implemented/reviewed. A manual rotation test is not proof of protection against a malicious restore operator or correlated loss of both stores.

A restarted worker must claim a new SQL fence. It may recover current typed evidence, but cannot borrow an old HTTP/inference admission lease. `CheckpointIssuer` creates separate non-dispatchable source checkpoints that survive the original action's revocation, clipped to that source's remaining original lifetime rather than a new600-second window. `restore_interpretation` constructs fresh validator dependencies and never calls a live model. Changed/unknown result, source or missing raw provenance blocks. A fresh current application action and all financial/provider checks are still required.
